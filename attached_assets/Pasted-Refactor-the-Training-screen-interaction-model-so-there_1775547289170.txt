Refactor the Training screen interaction model so there is only ONE clear natural-language entry point for the user.

CORE PRODUCT PRINCIPLE
This product should feel like querying a trusted coach, not using a collection of AI tools.
It must stay grounded in our existing training philosophy, our pre-built program library, and our coaching logic.
It must NOT feel like a random GPT wrapper.

The coach should consistently apply:
- our existing programming philosophy
- our existing exercise and progression standards
- our existing library content where relevant
- Ockham’s razor
- simplicity over novelty
- clarity over feature sprawl

======================================
GOAL
======================================

Unify the current fragmented interactions on the Training screen into one single coach interface.

Right now we have multiple competing interaction methods:
- free text command box for scheduling / edits
- “Build From Library”
- “Build Through AI”

This is too cluttered and creates a messy mental model.

We want ONE primary interaction:
- “Ask your coach”

Everything else should either:
- be removed from primary view
- be folded into the coach workflow
- or become a backend capability the coach can use automatically

======================================
NON-NEGOTIABLE OUTCOME
======================================

The user should not need to decide between:
- library
- AI
- command box
- builder

They should just ask.

The system should decide whether to:
- pull from the library
- adapt an existing template
- edit a current plan
- create a new week
- shift sessions around
- explain reasoning
- review training structure

The interface should feel like:
one coach, one brain, one place to ask.

======================================

The coach must remain:

- practical

======================================
4. COACH CAPABILITIES WITH ONE ENTRY POINT
======================================

The single “Ask your coach” interface should handle four broad categories of request:

A. PLAN
Examples:
- “Build me a 4 day upper/lower split”
- “Plan next week for 3 strength sessions and 2 runs”
- “Make me a simple hybrid plan”

B. ADJUST
Examples:
- “Move Friday’s session to Saturday”
- “I missed Monday, fix the rest of the week”
- “Swap this exercise because my elbow is flaring up”

C. PROGRESS
Examples:
- “Repeat this week for 4 weeks with progression”
- “Add progression to my squat work”
- “Make next week slightly harder”

D. REVIEW / EXPLAIN
Examples:
- “Is this week balanced?”
- “Why is this too much upper body?”
- “What am I missing here?”
- “Explain the progression”

All of these must route through the same coach layer.

- plan creation

6. LIBRARY AS BACKEND INTELLIGENCE
======================================

Keep the pre-built library as a core asset.

The coach should use the library first when appropriate.

Preferred behaviour:
- if a suitable library template exists, start there
- then adapt it to the user’s context
- only create from scratch when library coverage is weak or the request is highly specific

Examples:
User says:
- “Give me a 4 day strength plan”
Coach should:
- first look for the closest relevant internal template
- then adapt it

User should feel:
- they are getting the benefit of our proven systems
not
- random text generation

Do not expose internal implementation details unless useful.

- clear actions
- structured output

======================================
8. OCKHAM’S RAZOR RULES
======================================

This needs to be explicit in the logic.

When building or modifying training, the coach should prefer:
- fewer moving parts
- fewer unnecessary exercise swaps
- fewer progression variables at once
- repeatable session structures
- practical weekly rhythm
- plans that are easy to follow consistently

Examples of what to avoid:
- excessive exercise variety
- too many progression methods at once
- unnecessary complexity in periodisation
- changing things just to make it look clever
- over-customising when a simple template works

The coach should ask:
- what is the simplest effective structure here?
- what is easiest to adhere to?
- what preserves momentum?

======================================
10. COACH RESPONSE UX
======================================

The coach should not just dump text.

Responses should be structured by request type.

For example:

If user asks to build a plan:
- provide a concise summary
- show the proposed structure
- show any key assumptions
- allow confirm / apply

If user asks to adjust schedule:
- show exactly what will change
- allow confirm / apply

If user asks to review:
- provide short analysis
- identify key issue or approval
- suggest the simplest fix

If user asks for progression:
- explain how progression will be applied
- keep progression logic consistent with our existing methods

The coach should feel execution-oriented, not chatty.

======================================
11. GUARDRAILS
======================================

The coach must not:
- invent a brand new philosophy that conflicts with existing programming standards
- ignore the pre-built library when it is relevant
- create flashy but impractical plans
- overcomplicate sessions
- bloat the interface

If the user asks for something that conflicts with our philosophy:
- coach should gently constrain or redirect
- explain the simpler, more effective alternative

Example:
If user asks for a wildly overcomplicated structure,
the coach should simplify and explain why.
